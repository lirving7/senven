## 0. 决策摘要

| # | 决策点 | **裁决** | 关键理由 | 明确否决 | 影响面 |
|---|---|---|---|---|---|
| **D1** | 回流事实目标 | **只写 `Capability`，不回写 `Skill`** | Skill 是 Match 的输入且 MatchRun 是历史快照；回写会破坏历史匹配的可复现性 | 否决「同步写 Skill+Capability」（= AI 间接改写 Match 输入）；否决「只产候选不落库」（能力无法长期积累） | 新增不变量 I6；Match 输入源保持不变 |
| **D2** | 证据锚点 | **「项目成果」是 T3 新增事实回流的唯一证据锚点；它<ins>不是</ins> Capability 的唯一来源**（既有简历投影来源继续成立） | 现有 `Evidence` 无任何"成果"挂点，不定义锚点则 T3 回流无据可依 | 否决「复用 `ResumeProject` 承载成果」（简历经历 ≠ 执行产出，语义不同构）；否决"以 ActionStep 为锚"（见 D3） | 决定 T3 必然包含 1 个新实体；**能力来源为多路并存** |
| **D4** | 用户确认边界 | **候选事实一律落 `UNCONFIRMED`；`CONFIRMED` 仍只能由用户显式确认产生** | 延续「confirm 是唯一 CONFIRMED 路径」铁律 → 事实安全模型无需重写 | 否决「有外部链接即可直推 CONFIRMED」（链接不能证明归属，可指向他人仓库）；否决 AI 直写 CONFIRMED | 事实安全模型不变；闭环必须含"用户确认"一跳 |
| **D3** | 完成 ≠ 事实 | **产生候选能力的唯一触发 = 用户从某个 ActionStep 显式提交项目成果（含证据）**（措辞依 D6-a 对齐） | 与已接受的「Step DONE ≠ Fact」一致 | 否决「以 DONE 步骤数推断能力」；否决「AI 判断完成度」 | 回流需"用户显式提交"动作 |

| **D6** | 可追溯性（含 **D6-a**） | **必须建立完整 provenance：`Capability → Evidence → 项目成果 → ActionStep`，且用户可查看「这个能力为什么存在」。**<br>**D6-a：T3 v1 内，Project Result 必须可追溯到唯一来源 ActionStep（强绑定）；"独立于 ActionStep 的成果回流"明确延期 T3+。** | 事后补建成本极高；它是事实安全对用户可见的证明。强绑定使 I7 的 provenance 链在 v1 内**始终闭合**，可机械验证 | 否决「仅存摘要 / 不建链」；否决「允许独立提交」（软绑定会诱发"随便指定一个步骤"→ 形式绑定、语义失真，反而污染 provenance） | 成果必须携带来源步骤引用（形态属实现） |

## 1. 数据流（正向 + 反向，含封闭边界）

### 正向：既有链（T2 + 桥接，已验收，不得破坏）

```
简历事实 ──用户确认──→ Skill CONFIRMED
                            │
                            │ C2 单向投影（幂等）
                            ▼
                        Capability ──────┐          ┌──── 来源之一：RESUME_PROJECTION
                            ▲            │          │
                            │            │ C3 生成前 reconcile
                            │            ▼
                            │      ActionPlan.have
                            │            │
                            │            ▼
                            │       ActionStep
                            │            │ C4
                            │            ▼
                            │     学习 / 实践 / 项目入口
                            │            │
                            │            ▼
                            │      【用户实际执行】
                            │
┌───────────────────────────┘
│
│  T3 新增（正向回流）
│
│  用户**从某个 ActionStep** 显式提交「项目成果」+ 证据   ← D3 + D6-a（强绑定，唯一来源）
│            │
│            ▼
│      项目成果 ── 必可追溯到来源 ActionStep              ← D2（T3 新增回流的唯一证据锚点）
│            │
│            │ AI 分析生成（可失败 / 可跳过）
│            ▼
│      候选能力（UNCONFIRMED）                            ← D4
│            │
│            │ 用户显式确认 + 存在可核验证据
│            ▼
└──→  Capability（CONFIRMED）  ← 同一 (userId,key) 可被「简历投影」与「成果回流」**多来源共同支撑**（D5）
```

### 反向：**必须保持封闭**（本 Freeze 的硬边界）

```
Capability  ──✗──→  Skill          （D1：禁止回写）
ActionStep  ──✗──→  Capability      （D3：DONE 不产生事实）
ActionStep  ──✗──→  Skill           （同上）
候选能力    ──✗──→  CONFIRMED       （D4：必须经用户确认）
独立成果    ──✗──→  Capability      （D6-a：T3+ 才开放）
```

**边界含义**：`Match` 的输入源始终是 V1 事实层（Skill），**T3 不改变 Match**。

## 2. 状态机

### 2.1 事实状态（`FactStatus`：既有枚举，不变）

```
                  AI 产出候选
   (无) ─────────────────────────→ UNCONFIRMED
                                      │
             用户显式确认 + 有可核验证据 │  ← 唯一通往 CONFIRMED 的边
                                      ▼
                                  CONFIRMED
                                      │
                      只可"加强"（追加证据 / 提升等级，append-only）
                                      │
                                      └──✗──→ 不得静默降级 / 不得回到 UNCONFIRMED
```

- `INFERRED` 语义保留给「从**既有已确认事实**推断」的场景（与现有简历解析一致）；**T3 的 AI 候选统一写 `UNCONFIRMED`**，不复用 `INFERRED`，避免语义重叠。
- **不存在** `UNCONFIRMED → CONFIRMED` 的自动边。

### 2.2 ActionStep 状态（既有：TODO / IN_PROGRESS / DONE）

```
TODO → IN_PROGRESS → DONE
                       │
                       ├──✗──→ 不产生 / 不修改任何事实（I2，C5 已固化）
                       └──→ 可作为「提交项目成果」的来源锚点（D6-a：仅作为**归属**，不构成事实）
```

**两条状态机之间不存在任何"事实写入"边。** 事实状态只能由「用户确认」推进，任务状态只能由「用户操作」推进；ActionStep 对事实的唯一作用是**提供归属上下文**，而非触发。

## 4. 验收标准

### R1–R9（沿用并细化 `docs/t2-t3-bridge-acceptance.md` 已登记的 T3-R1~R5）

| # | 验收标准 |
|---|---|
| **R1** | **证据锚点**：项目成果实体存在，且其证据关联可持久化、可追溯 |
| **R2** | **回流必须带可核验证据**：无证据（或证据为空记录）不得产生任何候选能力 |
| **R3** | **幂等**：同一次成果重复提交不得产生重复能力或重复证据 |
| **R4** | **可追溯**：新能力能追溯到来源成果，**并可继续追溯到来源 ActionStep**（v1.1 补注：D6-a 强绑定下该链必须闭合；对应 I7） |

| **R6** | **完成≠事实**：将 ActionStep 全部置 `DONE` 后，能力数量与 Skill 状态**均不变**（与 I2 一致） |
| **R7** | **不回写 Skill**：任何回流路径执行后，`Skill` 表内容**逐字段不变**（I6） |
| **R8** | **多来源共存**：同一能力被「简历投影」与「成果回流」两路命中时，**收敛为一条**且两路证据**均在**、可分辨来源（D5） |
| **R9** | **能力只可加强**：追加证据后能力等级不得下降；不存在静默降级路径（I5） |
| **R10** | **死脚手架已清理**：`KnowledgeGap` / `CareerGoal` 不再存在于 schema 与数据库（D7）——**属 T3 实施阶段验收项**，非 Freeze 运行时验收 |

## 6. 风险检查项（**只检查，不裁决**）

> 本项源自议程中发现的 **D1 × D4 组合风险**。它不是一条裁决，而是一份**必须在 Freeze 审查与 T3 实施时反复执行的检查表**。

**危险路径（必须被封闭）**：

```
ActionStep DONE
   → AI 推断"已完成"
   → CONFIRMED Capability
   → Skill CONFIRMED
   → Match 结果改变
```

**逐跳检查表**：

| 跳 | 检查问题 | 本 Freeze 下的状态 |
|---|---|---|
| ① | `ActionStep DONE` 是否触发任何事实写入？ | **已封闭**（D3 + I2 + R6） |
| ② | AI 推断能否直接产生 `CONFIRMED`？ | **已封闭**（D4：候选一律 `UNCONFIRMED` + R5） |
| ③ | `CONFIRMED Capability` 是否允许进入 `Skill`？ | **已封闭**（D1：禁止回写 + I6 + R7） |
| ④ | Match 输入是否会因 T3 而变化？ | **不会**（因 ③ 封闭） |

**⚠️ 触发条件**：**若日后重新讨论 D1（是否回写 Skill），本检查表必须整体重跑** —— 因为在 D1 放开的假设下，③ 变成开放边，整条危险路径会立刻复活。

### 6.1 已知取舍（两条，均为**有意接受的切片限制**）

| 取舍 | 内容 | 正确解法（已延期，不得绕过） |
|---|---|---|
| **T-1（源于 D1）** | 用户完成项目、能力已 `CONFIRMED` 后，**重新对同一 JD 做 Match 仍会显示该项 MISSING**（Match 只读 Skill） | 将 **Match 输入源升级为 Capability** → 延期 T3+ 独立决策；**不得**通过回写 Skill 绕过 |
| **T-2（源于 D6-a）** | 与任何 ActionStep 无关的真实成果，在 T3 v1 内**无法回流** | 开放"独立成果回流" → 延期 T3+（届时 ActionStep 变为可选来源） |

## 7. 冻结项清单（通过后不得擅改）

1. **D1** 只写 `Capability`，不回写 `Skill`
2. **D2** 「项目成果」是 **T3 新增事实回流的唯一证据锚点**，**不是** Capability 的唯一来源
3. **D4** 候选一律 `UNCONFIRMED`；`CONFIRMED` 仅由用户确认产生
4. **D3** 候选能力的唯一触发 = 用户**从某个 ActionStep** 显式提交含证据的成果
5. **D5** 能力证据 append-only；能力只可加强；**同一 `(userId,key)` 多来源共存、来源不覆盖、provenance 可区分**（存储形态属数据模型设计）
6. **D6 / D6-a** 完整 provenance + 用户可见"能力为什么存在"；**Project Result 强绑定唯一来源 ActionStep**（独立成果延期 T3+）
7. **D7** 清理 `KnowledgeGap` / `CareerGoal`
8. **D8** §5 的 IN/OUT scope 与配额复用方案
9. **I1–I7** 不变量清单（T3 新增 3 条须各有自动化断言；**I5 含"算法延期"注记**）
10. **R1–R10** 验收标准（R4 含对 ActionStep 的追溯；R10 属实施阶段验收）
11. **§6 风险检查表**及其触发条件（D1 一旦重议即重跑）
12. **§6.1 两条已知取舍** T-1 / T-2

**冻结项之外，明确仍开放**：T3+ 的「Match 输入源是否升级为 Capability」、T3+ 的「独立成果回流」、以及全部数据模型/存储形态设计。
