# T3 架构冻结 · 议程（v1）

> **目的**：定义「必须裁决什么」——**只列决策点，不做裁决、不做设计**。
> **本议程明确不含**：数据模型设计、schema 变更、状态机实现、代码、对 D1~D8 的任何结论。
> **下一步**：本议程经你确认后，据以产出《T3 Architecture Freeze v1》。

---

## 0. 使用方式

每个决策点统一含五项：**决策问题 / 为何必须冻结 / 候选方向（仅列举）/ 影响面 / 依赖**。

- **根决策（必须先裁）**：**D1、D2、D4** —— 其余 5 项受其结论约束，先裁可避免返工。
- **每项裁决须记录**：选定方向 **+ 明确否决的方向与理由**（防止日后反复）。
- 候选方向一律**只列举不评价**；评价与选择在 Freeze v1 阶段进行。

## 1. 决策点清单

### D1 · 回流事实目标 〔根决策〕
- **决策问题**：项目成果产生的「能力」，写入哪个事实系统？
- **候选方向**：① 只写 `Capability`　② 同步写 `Skill + Capability`　③ 只产出"候选"不落库（需与 D4 联动）
- **为何必须冻结**：方向 ② 会**连带改变 Match 的输入**（Match 读的是 V1 事实层），使历史匹配结果的可复现性受影响。
- **已核实事实**：`Skill`（V1）驱动 Match；`Capability`（V2）驱动 ActionPlan；两者为**两套事实**，目前仅存在**单向投影** Skill→Capability。
- **影响面**：决定 T3 是否会"反写 V1"，以及 Match 是否需要版本化。
- **依赖**：无（根决策）。约束 D3 / D5 / D6 / D8。

### D2 · 证据锚点 〔根决策〕
- **决策问题**：什么实体代表「项目成果」？`Evidence` 如何与该实体关联？哪些来源算**有效证据**？
- **候选方向**：① 新增"成果"实体并挂证据　② 复用 `ResumeProject` 承载成果　③ 外部凭据型证据（仓库 / 部署 / 文档链接）单列
- **为何必须冻结**：不定义成果实体，就无法定义"什么叫完成了一个项目成果"，回流将失去事实锚点。
- **已核实事实**：`Evidence` 目前只能挂 `skill` / `resumeProject` / `education` / `experience` 四类 —— **不存在任何"成果"挂点**。
- **影响面**：直接决定 **是否产生 schema 变更** 及其范围。
- **依赖**：无（根决策）。约束 D3 / D5 / D6 / D8。

### D4 · 用户确认边界 〔根决策〕
- **决策问题**：AI 生成的候选事实，什么状态可直接落库？何时才允许 `CONFIRMED`？
- **候选方向**：① 候选一律 `UNCONFIRMED`，待用户确认　② 允许自动落到 `INFERRED`　③ 具备外部可核验凭据时可跳过用户确认直推 `CONFIRMED`
- **为何必须冻结**：方向 ③ 等于引入**"平台事实"**（未经用户确认的事实）——这是**事实安全的分水岭**，一旦允许，前两阶段建立的"confirm 是唯一 CONFIRMED 路径"铁律将被打破。
- **已核实事实**：现有铁律 = `confirm` 是唯一能把事实推到 `CONFIRMED` 的路径，且必须有 ≥1 条可核验证据。
- **影响面**：决定 T3 事实安全模型是否需要重写，以及是否存在"越权事实"风险。
- **依赖**：无（根决策）。约束 D3 / D5 / D8。

### D3 · 完成 ≠ 事实
- **决策问题**：`ActionStep DONE` 明确**不得**触发任何事实更新；那么，**什么条件才允许产生新的 Capability**？
- **候选方向**：以"成果 + 有效证据"为唯一触发　/　以"用户显式提交成果"为触发　/　其他
- **为何必须冻结**：这是 D2 的下游；若触发条件含混，回流会退化为"点完成即得能力"。
- **已核实事实**：**C5 已把「Step 置 DONE 不产生 Capability、不改 Skill」固化为自动化测试约束**（反向不变量）。
- **影响面**：回流触发点的定义、以及是否需要在成果侧设置"用户显式提交"动作。
- **依赖**：受 D2 约束。

### D5 · 幂等与版本
- **决策问题**：① 同一成果重复提交如何避免重复 `CapabilityEvidence`？② `Capability` 的 `level` / `source` / `evidence` 如何更新？③ **简历投影与成果投影如何共存**（同一 `key` 被两路来源命中时的合并规则与优先级）？
- **候选方向**：合并（同一 key 收敛为一条、证据合并且可追溯多来源）　/　不合并（来源分列、独立条目）　/　来源覆盖（后者覆盖前者）
- **为何必须冻结**：桥接阶段已建立 `Skill→Capability` 单向投影；T3 会新增第二条投影来源，两条来源必然在 `(userId, key)` 上相遇。
- **已核实事实**：`Capability` 的唯一键 `@@unique([userId, key])` 已强制收敛；现有投影已实现"无变化不写库"。
- **影响面**：决定 `Capability.source` 是否必须从"单值"改为"多来源"，以及证据去重键的定义。
- **依赖**：D1、D2。

### D6 · 可追溯性
- **决策问题**：是否需要完整 provenance 链 `Capability → Evidence → 项目成果 → ActionStep`？用户能否看到「**这个能力为什么存在**」？
- **候选方向**：完整双向可追溯　/　仅单向（能力→证据）　/　不建链（仅存摘要）
- **为何必须冻结**：provenance 一旦事后补建成本极高；且它是"事实安全"对用户可见的证明。
- **影响面**：是否新增溯源字段/表；以及前端"能力详情"的展示能力。
- **依赖**：D2。

### D7 · 死脚手架裁决
- **决策问题**：`KnowledgeGap`、`CareerGoal` —— **复用、改造，还是清理**？（必须给出明确定义，不能继续悬空）
- **候选方向**：复用并定义语义边界　/　改造后复用　/　清理（需 migration 删除）
- **为何必须冻结**：两表已存在于数据库与 migration，长期无定义会持续制造"看起来能用其实无用"的误导。
- **已核实事实**：两表已在 `schema.prisma` 与 migration 中存在，但 `src` / `app` **零引用**。
- **影响面**：清理需 migration；复用需明确与 T3 新实体的语义分工（避免一词两义）。
- **依赖**：无（可独立裁决）。

### D8 · T3 数据模型与配额边界
- **决策问题**：① 是否新增 `LearningTask` / `Project` / `ProjectResult` / `Portfolio`？② 是否复用已预置的 `LEARNING` / `PROJECT_MENTOR` / `PORTFOLIO` 配额槽？③ 哪些属于 **T3**、哪些**继续延期**（→ T3+/T4）？
- **候选方向**：按实体逐个 in/out　/　先只做最小实体集　/　全部延期（只冻结不实现）
- **为何必须冻结**：这是 T3 的范围边界；不定则无法给出 IN / OUT scope。
- **已核实事实**：`LLM_FEATURE.LEARNING`(10/日)、`PROJECT_MENTOR`(10/日)、`PORTFOLIO`(5/日) 配额**已预置但无任何 handler 使用**。
- **影响面**：T3 的 migration 规模与实现工作量。
- **依赖**：D1、D2、D4。

## 2. 决策顺序与依赖

```
根决策（先裁）
  D1 回流事实目标 ──┐
  D2 证据锚点 ──────┼──→ D3 完成≠事实
  D4 用户确认边界 ──┘      │
                            ├──→ D5 幂等与版本
                            ├──→ D6 可追溯性
                            └──→ D8 数据模型与配额边界

独立
  D7 死脚手架裁决
```

**你提出的"第 1、2、4 项最先裁决"我确认成立**，并补充其理由：D1 决定"写哪套事实"、D2 决定"事实挂在哪"，二者共同决定**数据模型的形状**；D4 决定"谁能造事实"，它决定**事实安全模型是否要改**。这三项一旦定了，D3/D5/D6/D8 都是在其上做推导，而不是独立设计。

**一个需要你注意的耦合**：D1 与 D4 存在相互作用 —— 若 D1 选"同步写 Skill"且 D4 选"允许自动 CONFIRMED"，则等于**AI 可以间接改写 Match 的输入事实**。这个组合的风险量级与分别选择时不同，建议裁决时**作为组合一并评估**，不要逐项孤立裁决。
